# [와르르랩] MCP 개발로그: 프롬프트를 계속 바꿨는데도 1메시지 = 1블록이던 진짜 이유

MCP 서버에서 DevTalk 대화를 block으로 구조화하는 테스트를 계속 돌려봤는데, 결과가 이상했다.  
프롬프트를 길게도 바꿔보고, 짧게도 줄여보고, APPEND를 강하게 유도하는 방향으로도 수정했는데 결과는 계속 같았다.

결과는 항상 이랬다.

- appendCount = 0
- newBlockCount = 100
- finalBlockCount = 100

즉, **메시지 100개를 넣으면 블록도 100개가 만들어지는 상황**이었다.  
처음에는 당연히 프롬프트 문제라고 생각했다.  
"같은 이슈의 문제 -> 가설 -> 시도 -> 결과 -> 인사이트를 하나의 블록으로 묶으라"는 규칙이 약해서 그런 줄 알았다.

그런데 이번 디버깅을 하면서, 원인이 프롬프트 자체가 아니라는 걸 확인했다.

## 1. 처음 의심한 것: 프롬프트가 약해서 과분할되는 것 아닐까?

현재 MCP의 역할은 단순 요약이 아니라, DevTalk 메시지를 DevLog에서 쓸 수 있는 narrative block 단위로 나누는 것이다.  
그래서 기대한 구조는 이런 식이었다.

예를 들어 로그인 500 에러를 추적하는 흐름이라면:

- 문제 발견
- 원인 가설
- mapper 확인
- null 방어 추가
- DB row 확인
- 가입 로직 수정
- 정상 동작 확인

이 전체가 하나의 이슈 흐름이기 때문에 하나의 block으로 묶이는 것이 자연스럽다.

하지만 실제 테스트에서는 이 흐름도 전부 각각의 block으로 쪼개졌다.  
그래서 처음에는 "프롬프트가 너무 보수적으로 NEW_BLOCK을 고르는 것 아닐까?"라고 생각했다.

## 2. 프롬프트를 계속 바꿨는데 결과가 똑같았다

프롬프트를 여러 번 바꿨다.

- 긴 규칙형 프롬프트
- APPEND를 더 강하게 유도하는 프롬프트
- qwen2.5:3b용 초압축 프롬프트
- 예시를 줄인 프롬프트
- `If uncertain, choose APPEND`를 넣은 프롬프트

그런데 결과는 계속 같았다.

처음에는 "qwen2.5:3b가 프롬프트를 잘 못 따르나?" 싶었는데, 여기서 이상한 점이 있었다.  
**프롬프트가 바뀌어도 결과 패턴이 너무 똑같았다.**

이쯤 되니 "진짜 프롬프트가 적용되고 있는 게 맞나?"부터 의심하게 됐다.

## 3. 실제로는 프롬프트 파일이 적용되지 않고 있던 구간도 있었다

Docker 환경에서 MCP는 프롬프트 파일을 환경변수로 읽도록 바꿔둔 상태였다.

우선순위는 이런 식이었다.

1. `MCP_NARRATIVE_PROMPT_FILE`
2. `MCP_NARRATIVE_PROMPT_TEMPLATE`
3. 코드 기본 프롬프트

그런데 실제 컨테이너 안을 확인해보니, 환경변수는 `/prompts/narrative_router.txt`를 가리키고 있었지만  
정작 mount된 파일은 `narrative_router.example.txt`만 있었다.

즉 한동안은:

- env는 맞게 넣어둠
- 컨테이너 mount도 됨
- 하지만 파일명이 안 맞음
- 그래서 코드가 원하는 파일을 못 읽음
- 결국 기본 프롬프트로 계속 동작

이 상태였다.

솔직히 이 구간은 완전히 쉐도우 복싱이었다.  
"프롬프트를 바꿨다"고 생각했는데 실제론 바뀐 프롬프트가 한 번도 적용되지 않은 상태였기 때문이다.

## 4. 그런데 프롬프트를 진짜 적용한 뒤에도 결과는 여전히 같았다

프롬프트 파일명을 맞추고, 컨테이너 안에서 실제 파일 내용까지 확인했다.  
즉 이 시점부터는 "프롬프트가 반영되지 않았다"는 가설은 버릴 수 있었다.

그런데도 결과는 여전히 같았다.

- appendCount = 0
- reason = `fallback_conservative_new_block`

여기서 핵심 단서를 잡았다.  
문제는 모델이 APPEND를 안 고르는 것이 아니라, **실제 라우팅 호출이 실패해서 fallback으로 계속 내려가고 있다는 점**이었다.

## 5. 실제 원인: 긴 narrative routing 호출이 timeout 나고 있었다

이걸 확인하려고 MCP 컨테이너 안에서 Ollama direct call을 직접 돌려봤다.

확인 결과는 이랬다.

- 짧은 prompt + JSON 출력: 성공
- 짧은 prompt + schema(format): 성공
- 실제 narrative routing prompt + candidateBlocks + recentMessages + schema: timeout

즉 qwen2.5:3b가 JSON을 못 만드는 게 아니었다.  
짧은 요청은 충분히 처리했다.

문제는 **실제 라우팅 prompt가 너무 많은 걸 한 번에 요구하고 있었다는 점**이다.

현재 구조는 1단계에서 동시에 이걸 다 시키고 있었다.

- APPEND / NEW_BLOCK 판단
- targetBlockId 선택
- blockType 생성
- status 생성
- topic 생성
- summary 생성
- tags 생성

작은 로컬 모델 입장에서는 너무 무거운 요청이었다.  
결국 timeout이 나고, 코드에서는 이 예외를 잡아서 `_fallback_narrative_classification()`으로 내려간다.  
그리고 현재 fallback은 보수적으로 항상 `NEW_BLOCK`을 반환한다.

그래서 최종 결과가 계속 "1 message = 1 block"이 된 것이다.

## 6. 이번에 얻은 결론

이번 디버깅에서 가장 크게 배운 점은 이거다.

**프롬프트 품질 문제처럼 보이는 현상도, 실제로는 모델 호출 구조 문제일 수 있다.**

처음에는 계속 프롬프트 문장을 고치는 데 집중했다.  
하지만 실제 원인은 다음 두 가지였다.

1. 한동안은 프롬프트 파일이 아예 적용되지 않고 있었다.
2. 적용 후에도 실제 narrative routing 호출 자체가 모델에게 너무 무거워 timeout이 나고 있었다.

즉 문제의 핵심은  
"APPEND를 잘 유도하는 문장을 어떻게 쓸까?"  
보다  
"작은 로컬 모델에게 한 번에 얼마나 적은 일을 시킬까?"  
에 더 가까웠다.

## 7. 다음 단계: 라우팅과 메타데이터 생성을 분리할 계획

이제 방향은 명확하다.

현재처럼 한 번에 전부 생성하는 구조 대신, 2단계로 분리하는 쪽이 맞다.

### 1단계: 라우팅 전용

이 단계에서는 딱 이것만 판단한다.

- APPEND / NEW_BLOCK
- targetBlockId
- score
- reason

즉 "붙일지, 새로 만들지"만 빠르게 안정적으로 판단하게 한다.

### 2단계: 메타데이터 생성

그 다음 단계에서 따로 처리한다.

- blockType
- status
- topic
- summary
- tags

이건 규칙 기반으로 처리할 수도 있고, 정말 필요하면 더 짧은 별도 prompt로 분리할 수도 있다.

작은 로컬 모델을 쓸수록, 한 번에 많은 걸 시키기보다  
**판단을 여러 단계로 쪼개는 구조가 더 현실적**이라는 걸 이번에 확실히 느꼈다.

## 마무리

이번 디버깅은 단순히 "프롬프트를 잘 써야지" 수준의 문제가 아니었다.  
실제로는:

- Docker env 주입 구조
- mount된 프롬프트 파일 경로
- Ollama direct call
- schema 강제
- timeout fallback

까지 전부 확인해야 했다.

결국 지금 문제는  
"프롬프트가 나빠서 과분할된다"  
가 아니라  
**"현재 narrative routing 호출 구조가 qwen2.5:3b에게 너무 무겁다"**  
로 정리할 수 있다.

다음 글에서는 이 문제를 해결하기 위해  
**라우팅 전용 1단계 구조로 어떻게 바꿀지**를 정리해보려고 한다.
