# Git 컨벤션

**작성일:** 2026-08-24
**적용 범위:** 이 저장소의 모든 브랜치·커밋·PR
**근거:** Google 커밋 메시지 관례
(<https://google.github.io/eng-practices/review/developer/cl-descriptions.html>)

이 문서가 없으면 매번 다른 모양의 커밋이 쌓이고, 6개월 뒤에 히스토리로
"왜 이렇게 했나" 를 되짚을 수 없게 된다. 히스토리는 문서가 못 남기는 것을
남기는 자리다 — **그때의 판단 근거**.

---

## 1. 커밋 제목

```
<type>: <무엇을 했는가>
```

- **72칸 이내.** 한글은 2칸으로 센다. 넘으면 목록 화면에서 잘린다.
- **끝에 마침표를 찍지 않는다.**
- **무엇을 했는지**를 적는다. "고침" 이 아니라 "무엇을 어떻게 고쳤는지".
- 파일 이름 나열은 제목이 아니다. `git diff --stat` 이 이미 보여준다.

Google 관례는 접두사를 요구하지 않지만, 이 저장소는 `<type>:` 를 붙인다.
히스토리 앞부분이 이미 그렇게 쌓였고, 한 줄 목록에서 성격을 훑기 좋다.
**둘 중 하나를 고르는 문제이므로 섞지 않는다.**

### type 목록

| type | 언제 |
|---|---|
| `feat` | 사용자가 쓸 수 있는 것이 늘어남 |
| `fix` | 잘못 동작하던 것을 고침 |
| `refactor` | 동작은 그대로, 구조만 바꿈 |
| `test` | 테스트만 |
| `docs` | 문서만 |
| `chore` | 빌드·의존성·설정 |

`refactor` 와 `fix` 가 헷갈리면 **테스트가 늘었는지**로 가른다.
동작이 달라져서 새 테스트가 필요하면 `fix` 또는 `feat` 다.

---

## 2. 커밋 본문

제목 다음 **빈 줄 하나**, 그리고 본문. 본문은 **72칸에서 접는다.**

본문이 답해야 하는 것은 하나다 — **왜 이렇게 했는가.**
무엇을 바꿨는지는 diff 가 이미 말한다. diff 가 말하지 못하는 것만 적는다.

- 어떤 문제가 있었나 (재현 조건까지)
- 왜 이 방법인가, **버린 대안은 무엇이고 왜 버렸나**
- 알고 받는 한계는 무엇인가

본문이 필요 없는 커밋도 있다. 오타 수정에 다섯 문단을 쓰지 않는다.
다만 **판단이 하나라도 들어간 커밋에는 본문이 있어야 한다.**

### 예시

```
fix: 404 를 spool 로 돌려 새 기록이 조용히 사라지지 않게 한다

_NO_SPOOL_STATUSES 에 404 가 들어 있었다. SingleInstanceLock 때문에
구버전 데몬이 떠 있으면 _spawn_daemon 이 새로 띄우지 않으므로,
새 라우트를 모르는 데몬에 닿는 순간 새 기록만 404 를 받고
spool 도 dead-letter 도 없이 사라진다(OUTSTANDING K2).

버린 대안: 데몬 버전 핸드셰이크. 요청마다 왕복이 하나 늘고,
막으려는 상황은 업그레이드 직후 몇 분뿐이라 값이 안 맞는다.

알고 받는 한계: 영구적 404 는 spool 에 계속 쌓인다(K9 로 열어 둠).
```

## 3. 커밋 크기

**하나의 커밋은 하나의 판단이다.**

되돌릴 때 함께 되돌아가야 하는 것만 한 커밋에 넣는다.
"테스트 먼저 쓰고 구현" 은 한 판단이므로 한 커밋이다 — 테스트만 있는
커밋은 그 자체로 빨간 상태라 되돌릴 지점이 되지 못한다.

반대로 **한 태스크를 한 커밋에 몰아넣지 않는다.** 리뷰가 어려워지고,
그중 한 줄이 잘못됐을 때 나머지까지 되돌려야 한다.

기준: `git show <sha>` 를 열었을 때 **한 화면에서 판단이 읽히면** 적당하다.

## 4. 브랜치

```
<type>/<무엇>
```

- `feat/topic-screen` · `fix/spool-404` · `docs/git-convention`
- 소문자, 하이픈 구분, 영문. 한글은 도구마다 인코딩이 달라 쓰지 않는다.
- **기능 하나에 브랜치 하나.** 태스크가 크면 태스크 안에서 더 쪼갠다.

`master` 가 기본 브랜치다. `master` 에 직접 커밋하지 않는다.

---

## 5. PR

- 제목은 커밋 제목과 같은 규칙을 따른다.
- 본문에는 **무엇을 검증했는지**를 적는다. 테스트 수와 실측 결과.
- 머지는 **squash** 다. 브랜치 안의 시행착오가 `master` 히스토리에 남으면
  "하나의 커밋은 하나의 판단" 이 깨진다.
- 머지 후 브랜치를 지운다. 로컬은 `git checkout master && git pull` 로 따라간다.

## 6. 머지 조건

**예외 없다.**

- `python -m pytest -q` 가 `local/` 에서 전원 통과
- 완료 조건이 산문이 아니라 **통과하는 테스트 이름**으로 적혀 있을 것
  (계획 문서 규칙과 같다)

---

## 7. 이 문서를 고칠 때

컨벤션을 바꾸면 **과거 커밋을 고치지 않는다.** 히스토리는 그때의 규칙으로 읽는다.
바꾼 날짜와 이유를 여기 적고, 그 뒤 커밋부터 새 규칙을 적용한다.
