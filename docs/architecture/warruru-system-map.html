와르르랩 시스템 지도

여덟 개의 서비스가 문서로 정의돼 있고, 그중 하나만 실제로 돕니다. 무엇이 무슨 일을 하고, 기록 한 건이 어떤 경로로 저장되는지를 정리했습니다.

8명세가 있는 서비스
1코드가 있는 축 (local/)
25테스트 파일 (pytest)
1진행 중인 조각 (학습 기록)
01

지금 상태 — 문서와 코드의 간극

와르르랩은 문서 우선(Documentation-First) 원칙으로 시작했습니다. 그 결과 명세서는 여덟 벌이 갖춰졌지만, 실제로 실행되는 코드는 루트의 local/ 한 곳뿐입니다. 나머지는 아직 AGENTS.md와 요구사항·기능·인터페이스 명세만 있습니다.

그래서 이 지도는 두 층으로 나뉩니다. 위층은 오늘 돌아가는 것, 아래층은 설계만 되어 있는 것입니다.

02

서비스별 역할과 주고받는 것

local/ (warruru-local) 동작 중

AI 에이전트가 남기는 개발 기록을 개인 머신 SQLite 에 유실 없이 저장하고 날짜별 화면으로 되돌려 준다. 두 프로세스(어댑터·데몬)로 나뉜다.

받는 것 · MCP 툴 호출 (stdio)
내보내는 것 · SQLite 행, 웹 화면 HTML

packages/agent 명세만

학습 대화 · 지식 구조화 · 블로그 초안 · 기록 관리 네 모듈을 한 에이전트에 묶는 계획. 와르르랩의 원래 중심이지만 아직 코드가 없다.

받을 것 · 사용자 질문, RAG 검색 결과
내보낼 것 · 답변, 지식 블록, 초안

packages/web-ui 명세만

대화 · 지식 블록 · 초안 편집 · 기록 타임라인을 한 화면에서 다루는 통합 UI 계획. 지금 화면은 데몬이 직접 그리는 Jinja2 페이지가 대신하고 있다.

받을 것 · 에이전트 API 응답
내보낼 것 · 브라우저 화면

services/ollama 명세만

로컬 GPU 로 도는 LLM 서버. 빠른 응답용 소형 모델, 글 생성용 대형 모델, 임베딩 모델을 나눠 쓸 계획이다.

받을 것 · 프롬프트, 임베딩 요청
내보낼 것 · 생성 텍스트, 벡터

services/qdrant 명세만

지식 베이스의 벡터 저장소. 과거 학습 내용을 유사도로 찾아 대화에 근거를 붙이는 RAG 검색을 맡는다.

받을 것 · 임베딩 + 메타데이터
내보낼 것 · 유사 문서 목록

services/sync 명세만

Windows 와 Mac 을 오가며 작업할 때 결과물을 암호화 백업하고 병합·충돌 해결까지 맡는 동기화 계층.

받을 것 · 로컬 작업물
내보낼 것 · 원격 저장소 스냅샷

services/tistory-mcp 명세만

완성된 초안을 Tistory 에 발행하는 MCP 서버. OAuth 인증, 카테고리·태그 설정, 발행까지가 범위다.

받을 것 · 마크다운 초안
내보낼 것 · 발행된 글 URL

학습 기록 (진행 중) 설계 완료

local/ 안에 붙일 다음 조각. 실험 · 트러블슈팅 · 기술 선택 · CS 개념 네 종류를 면접에서 말할 수 있는 형태로 남긴다. 스펙과 구현 계획까지 나왔고 코드는 아직 없다.

받을 것 · MCP 툴 6개
내보낼 것 · 개선률, /records 화면

03

동작하는 축의 내부 구조

local/은 프로세스가 둘입니다. 에이전트마다 하나씩 뜨는 얇은 어댑터와, 머신당 하나 상주하는 데몬입니다. 이 분리가 이 시스템의 핵심 결정입니다 — 여러 에이전트가 동시에 기록해도 SQLite 에 쓰는 것은 언제나 데몬 하나뿐이라 잠금 경합이 생기지 않습니다.

04

데이터가 오가는 세 가지 경로

기록 하나가 남는 길은 데몬이 켜져 있느냐에 따라 갈리고, 읽는 길은 사람이냐 에이전트냐에 따라 갈립니다. 세 경로 모두 같은 함수로 수렴하도록 설계돼 있습니다 — 온라인 경로와 흡수 경로가 갈라지면 한쪽에만 있는 버그가 생기기 때문입니다.

경로 A · 데몬이 켜져 있을 때

  1. 에이전트가 MCP 툴을 부른다 (record_checkpoint 등)
  2. 어댑터가 식별자(ckp_…)와 시각을 만들어 POST /v1/checkpoints
  3. 데몬이 토큰을 확인하고, 활성 세션을 찾아 붙이고, git 상태를 수집한다
  4. 상한을 넘는 문자열은 자르고 SQLite 에 한 트랜잭션으로 쓴다
  5. storage: "DAEMON" 과 함께 결과를 돌려준다 — 에이전트가 사용자에게 보고

경로 B · 데몬에 닿지 못했을 때

  1. HTTP 요청이 실패한다 (데몬 꺼짐 · 5xx · 구버전이라 404)
  2. 어댑터가 대화별 JSONL 파일에 봉투 한 줄을 덧붙인다 — storage: "SPOOL"
  3. 데몬이 켜지거나 5분 스윕이 돌 때, 조용해진 파일을 이름부터 바꿔 붙잡는다
  4. 봉투를 경로 A 와 같은 함수에 넘겨 반영한다
  5. 전부 반영되면 absorbed/ 로 보관. 실패한 봉투는 남겨 재시도하고, 5회를 넘기면 dead-letter/ 로 격리한다

경로 C · 읽을 때

  1. 사람은 브라우저로 http://127.0.0.1:8787/d/2026-08-17 — 조회는 토큰이 필요 없다
  2. 삭제·복구처럼 상태를 바꾸는 폼만 토큰을 요구한다 (다른 사이트가 내 데몬을 조작하지 못하게)
  3. 에이전트는 get_today_context 로 그날 요약 마크다운을 받아 대화 맥락에 넣는다
05

지금 만들고 있는 조각 — 학습 기록

2027년 3월 공채를 목표로 한 31주 로드맵에서, 면접에서 말해야 할 것이 네 갈래로 생깁니다. 넷 다 지금 남길 곳이 없습니다.

  1. 측정값이 붙은 개선 — N+1 을 없앤 뒤 쿼리가 102개에서 3개로 줄었다는 사실. 숫자는 기억에 남지 않습니다.
  2. 장애와 해결 — 증상 → 원인 → 해결의 사슬은 며칠이면 흐려집니다.
  3. 기술 선택의 근거 — 실제로 가장 자주 묻는 것입니다. 후보를 늘어놓고, 각각의 장단점을 적고, 우리 프로젝트의 어떤 특성 때문에 이걸 골랐고, 고른 것의 단점을 어떻게 보완했는지까지가 한 덩어리입니다. 지금은 통째로 머릿속에만 있어서, 몇 주 지나면 "Kafka 를 썼습니다"만 남습니다. 그건 기술 이름을 나열하는 설명이고, 로드맵이 명시적으로 버리기로 한 방식입니다.
  4. CS 기초 — Java · 네트워크 · OS · DB · 알고리즘 · 자료구조, 그리고 포트폴리오에 쓰는 기술들. 2027년 상반기에 공부하면서 읽은 것을 내 말로 다시 쓴 문장이 남아야 합니다. 남의 문장은 면접장에서 안 나옵니다.

기존 checkpoint 테이블은 종류가 9개로 고정돼 있고 수치를 담을 자리가 없어, 새 테이블 세 개로 갑니다. 체크포인트가 작업 중의 순간이라면 학습 기록은 면접에서 말할 수 있게 정리된 것이고, 수명도 다릅니다 — 31주차에 다시 읽을 것들입니다.

더하는 것무엇왜
learning_record 문제 · 가설/원인 · 조치 · 선택 근거 · 단점 보완 · 결과 · 한계 · 면접 문장 · 분야 · 근거 원문 · 프로젝트 면접 서사 6단계와 필드 순서를 맞춘다
measurement 지표 이름 · 이전값 · 이후값 · 단위 · 방향 한 번의 개선이 쿼리 수와 p95 를 동시에 움직인다
tech_option 후보 이름 · 장점 · 단점 · 선택 여부 후보 2개 이상이 강제다. 후보가 하나면 그건 선택이 아니라 통보다
MCP 툴 6개 기록 4개 (실험 · 트러블슈팅 · 기술 선택 · CS 개념) + 조회 2개 기록 종류가 다르면 필수 필드도 다르다. MCP 스키마는 "조건부 필수"를 표현하지 못한다
/records 화면 프로젝트 · 주차 · 분야 · 태그 필터, 상세 6단계 + 후보 표, 복습 큐(면접 문장이 빈 기록만) 날짜 화면과 섞지 않는다. 수명이 다르다

기술 선택 기록 한 건이 화면에 보이는 모습

후보          장점                        단점                       선택
RabbitMQ     개별 ACK, DLQ 가 기본       처리량 한계, 재처리 불편     ●
Kafka        높은 처리량, 재처리 가능     오프셋 운영 부담, 무겁다     ○

왜 이걸 골랐나
  주문 이벤트가 초당 수백 건 수준이라 처리량은 병목이 아니었고,
  실패한 메시지를 개별로 재처리하는 쪽이 먼저 필요했다.

단점을 어떻게 보완했나
  처리량 한계는 큐 분리와 prefetch 조정으로 밀어냈고,
  재처리가 필요한 이벤트만 별도 저장해 수동 리플레이 경로를 뒀다.

면접에서 이렇게 말한다
  "…"                                        ⚠ 아직 안 적음
이 세 덩어리가 붙어 있어야 면접 답변 한 문단이 됩니다. 후보 표 · 선택 근거 · 단점 보완을 떨어뜨려 놓으면 다시 조립해야 하고, 조립은 면접장에서 안 됩니다. 그래서 한 기록·한 화면에 담습니다. 비어 있는 칸에는 배지가 붙어서, 목록을 훑을 때 채울 곳이 바로 보입니다.
거절이 이 조각의 유일한 예외입니다. 기존 원칙은 "기록 요청은 실패로 끝나지 않는다"였지만, 원인이 빈 트러블슈팅 기록과 후보가 하나뿐인 선택 기록은 없느니만 못합니다. 게다가 검증 없이 spool 에 넣으면 흡수 시점에야 실패하는데, 그때는 에이전트가 이미 사라진 뒤라 아무도 고칠 수 없습니다.
반대로 거절하지 않는 것도 정해 뒀습니다. 단점 보완과 면접 문장은 기록하는 시점에 아직 없을 수 있습니다. 거절하면 기록 자체를 안 하게 되고, 조용히 넘어가면 영영 안 채웁니다. 그래서 저장하되 배지를 붙이고, ?missing=interview 로 그것만 골라 볼 수 있게 했습니다 — 그게 복습 큐입니다.
06

설계상 이어질 흐름

명세만 있는 여섯 서비스가 채워지면 데이터는 아래처럼 흐를 예정입니다. 지금은 어느 화살표도 구현돼 있지 않습니다.

계획된 파이프라인 (미구현)

  1. 웹 UI 에서 학습 질문을 던진다
  2. Chat 모듈이 Qdrant 에서 과거 지식을 찾고 Ollama 로 답한다
  3. Structure 모듈이 대화를 지식 블록으로 구조화한다
  4. 블록을 임베딩해 Qdrant 에 다시 넣는다 — 다음 대화의 재료가 된다
  5. Draft 모듈이 블로그 초안을 만들고, 사람이 고친다
  6. Tistory MCP 가 발행하고, 결과 글은 blog/ 에 커밋된다
  7. Sync 가 Windows ↔ Mac 사이의 작업물을 맞춘다
순서는 뒤집혀 있습니다. 원래 계획의 중심은 packages/agent 였지만, 실제로 먼저 완성된 것은 기록 계층인 local/ 이었습니다. 학습 기록 조각도 이 축 위에 얹힙니다 — 신뢰성(spool · 중복 방지 · 잠금)은 이미 값을 치르고 확보한 자산이기 때문입니다.
