## 이 문서를 읽는 규칙

세 가지가 이번 개정에서 새로 못 박힌다.

- **체크박스 하나 = 코드 커밋 하나.** 1:1 로 대응하지 않는 체크박스는
  그 태스크가 존재하지 않는다는 뜻으로 본다. 계획과 히스토리가 갈라지면
  다음 세션의 에이전트가 어느 쪽을 믿을지 모르게 된다.
- **완료 조건은 산문이 아니라 통과하는 테스트 이름이다.**
  "동작한다"는 검증할 수 없고 `test_데몬이_꺼져있어도_기록이_spool에_남는다` 는 검증된다.
  테스트를 붙일 수 없는 태스크(0·1)는 그 사실을 태스크 안에 명시했다.
- **모든 커밋의 머지 조건은 기존 pytest 24파일 전원 통과다.** 예외 없다.

## Goal — 왜 자르는 축을 바꿨나

면접에서 말해야 할 것은 기술 이름이 아니라
"문제 → 선택 → 구현 → 측정 → 결과 → 한계" 여섯 단계다.
그 재료를 개발 중에 그 자리에서 남기고, 주제 단위로 묶어,
비공개 글 한 편으로 앉히는 한 바퀴를 이번에 닫는다.

이전 판(2026-08-17)은 **계층별**로 잘려 있었다 —
마이그레이션 → 순수 모듈 → 저장소 → 로직 → API → 화면.
그러면 마지막 태스크가 끝나기 전까지 눈에 보이는 것이 하나도 없고,
중간에 멈추면 남는 것이 테이블과 함수뿐이다.
지난번 실패("명세만 쌓이고 코드 0줄")와 모양이 같다.

이번에는 **수직 슬라이스**로 자른다. 한 태스크가 끝날 때마다
종단 경로가 한 뼘씩 자라고, 어디서 멈춰도 그때까지의 경로는 살아 있다.

- Task 6 이 끝나면 에이전트가 남긴 기록이 DB 에 앉는다.
- Task 7 이 끝나면 그 기록이 주제로 묶여 화면에 보인다.
- Task 8 이 끝나면 그 주제가 저장소 바깥의 마크다운 파일이 된다.
- Task 10 이 끝나면 그 글이 티스토리에 비공개로 앉는다.

기록 종류는 4종이고 **테이블 하나의 컬럼 값**으로만 구분한다.

| kind | 무엇을 남기나 |
|---|---|
| `EXPERIMENT` | 바꿔서 수치가 달라진 것 |
| `TROUBLESHOOTING` | 고장났다가 고친 것 |
| `TECH_CHOICE` | 여러 기술 중 고른 것 |
| `CONCEPT` | CS 를 공부하고 이해한 것 |

kind 별 필수 필드 강제는 이번에 하지 않는다. 이유는 아래 Global Constraints 에 있다.

## Global Constraints

모든 태스크에 암묵적으로 포함된다.

**기존 원칙 (v1 에서 이어짐)**

- 데몬은 SQLite 의 **유일한 writer** 다. 어댑터는 DB 에 직접 접근하지 않는다.
- MCP 툴은 **예외를 밖으로 던지지 않는다.** 어떤 내부 오류도 `{ok: false, ...}` 로 바꾼다.
- 어댑터에 비즈니스 로직을 두지 않는다. 세션 귀속·git 판단은 데몬에 있다.
- 시각은 반드시 주입 가능한 `Clock` 을 거친다. `datetime.now()` 를 직접 부르지 않는다.
- 상한을 넘는 문자열은 자른다. 요청을 거절하지 않는다.

**이번에 더하는 원칙**

- **기록은 거절하지 않는다.** 필수는 `kind`·`topic`·`title`·`body` 넷뿐이고,
  나머지가 비어도 저장한 뒤 응답에 결손 필드와 예시 재호출을 실어 보낸다.
  기록 여부가 100% 에이전트 재량인 구조에서 거절은
  '기록 안 하기'를 가장 안전한 선택으로 만든다.
  (이전 판의 "필수 필드가 비면 거절한다" 원칙을 뒤집은 것이다. 명세 §5.3)
- **집계·필터·글 생성은 예외 없이 `topic_slug` 기준이다.** 원문 `topic` 은 화면 표시용이다.
- **날짜 구간은 예외 없이 `clock.local_day_bounds()` 로 만든다.** 문자열을 직접 잇지 않는다.
  이 함수는 서머타임 끝 경계가 부정확하다(OUTSTANDING I5, 미해결).
  한국 시간대에는 드러나지 않으며, 고칠 때 한 곳만 고치면 `/d`·`/t`·`/c` 가 함께 낫는다.
  그래서 별도 계산을 만들지 않고 굳이 이 함수를 부른다.
- **`publish/` 는 `sqlite3` 와 `warruru_local.store.*` 를 임포트하지 않는다.**
  문서 관례가 아니라 AST 테스트 1개로 강제한다(Task 8).

**임포트 방향** — 깨면 안 되는 경계다.

```
mcp/  ──▶  최상위(topics, spool, clock, config, ids)
daemon/  ──▶  최상위, store/, publish/
mcp/  ──✗──▶  daemon/       (한 번도 임포트하지 않는다)
publish/  ──✗──▶  store/, sqlite3
```

**식별자**

| 종류 | 형식 | 만드는 쪽 |
|---|---|---|
| Learning Record | `rec_` + ULID(26자) | 어댑터(MCP) |
| Draft | `drf_` + ULID(26자) | 데몬 |

**열거값**

```text
learning_record.kind    EXPERIMENT | TROUBLESHOOTING
                        | TECH_CHOICE | CONCEPT
learning_record.source  MCP | SPOOL
learning_record.topic   자유 문자열(원문 보존)
learning_record.topic_slug  정규화된 집계 키
draft.status            DRAFT | PUBLISHED

spool 봉투 kind (1종 추가)
  learning_record
```

봉투가 한 종인 이유는 툴이 하나이기 때문이다.
`kind` 4종은 봉투 종류가 아니라 컬럼 값이라 `payload` 안에 들어간다.

**테스트 규약**

- 테스트 이름은 기존 관례대로 한국어 (`def test_기록이_저장되고_다시_읽힌다():`).
- 시간대에 의존하는 테스트는 `TZ` 를 고정한다.
  (`monkeypatch.setenv("TZ", "Asia/Seoul")` + `time.tzset()`)
- 검증은 `local/` 안에서 `python -m pytest -q` 로 돌린다.
- 태스크별로는 그 태스크의 테스트 파일만 지정해 돌린다.

**완료 상태의 기준선** — 시작 시점 테스트 파일 24개 전부 통과. 끝날 때도 전부 통과한다.

### 이 태스크가 실제로 잡아낸 것 — `mcp` 2.0.0 파손

첫 시도에서 테스트가 **수집 단계에서 깨졌다.** `pyproject` 가 `mcp>=1.16.0` 으로
상한 없이 열려 있어 새 머신에서 **2.0.0** 이 설치됐고, 2.x 에는
`mcp.server.fastmcp` 경로가 없다(`mcp.server` 하위가 `mcpserver` 등으로 재편됐다).
`mcp/server.py:8` 의 임포트가 실패해 `test_acceptance.py` · `test_mcp_tools.py` 두
파일이 통째로 수집되지 못했다.

`mcp==1.29.0`(1.x 최신)으로 내리자 248개가 전원 통과했다.
`pyproject.toml` 의 의존성을 **`mcp>=1.16.0,<2`** 로 고정하고 이유를 주석으로 남겼다.

이것이 Task 0 를 먼저 두기로 한 판단의 근거다. 이 단계를 건너뛰고 새 코드를 썼다면
"통과 중이던 248개"라는 안전망이 실제로는 처음부터 없었고, 이후의 모든
"됐다"가 근거를 잃었을 것이다. **2.x 로의 이관은 별도 결정이며 이번 범위 밖이다.**

## Task 2: K2 수정 — 새 기록을 얹기 전에 고친다

**목표:** 404 를 받은 쓰기 봉투가 spool 로 떨어지게 하고,
모르는 kind 봉투를 dead-letter 로 격리한다.

**왜 지금인가.** `mcp/client.py` 의 `_NO_SPOOL_STATUSES` 에 `404` 가 들어 있다.
`SingleInstanceLock` 때문에 구버전 데몬이 떠 있으면 `_spawn_daemon` 이 새로 띄우지 않으므로,
`/v1/records` 를 모르는 데몬에 닿는 순간 **새 기록만** 404 를 받고
spool 도 dead-letter 도 없이 조용히 사라진다.
확보했다는 오프라인 내구성을 새 기록 종류에 대해서만 정확히 우회하는 경로라,
새 코드를 얹기 전에 고쳐야 한다. 미루면 결함이 정확히 새 기능에서 발현된다.

**404 를 spool 로 돌리는 것만으로는 부족하다.** 위 두 수정은 새 데몬 안에 있는데,
K2 가 문제되는 상황은 정의상 **구버전 데몬이 떠 있는 상황**이다.
그 데몬의 스윕이 spool 파일을 집어 들고, `_HANDLERS` 에 `learning_record` 가 없어
경고만 남긴 채 `absorbed/` 로 옮겨 **한 겹 뒤에서 똑같이 사라진다.**

해법은 이미 코드에 있다 — `absorb_all` 은 파일을 붙잡기 전에
`_has_unknown_version(path)` 를 보고, 모르는 버전이 섞여 있으면
**이름조차 건드리지 않고 그대로 둔다.** 새 봉투에 버전 2 를 주면
구버전 데몬이 그 파일을 통째로 건너뛴다. 유실이 아니라 대기가 된다.
(명세 §4.5.1)

## 보류 — MVP 이후

이전 판(2026-08-17)의 태스크 중 이번 범위 밖으로 밀린 것들이다.
**삭제하지 않는다** — 되살릴 때 여기서 찾는다. 각 항목에 밀린 이유가 하나씩 있다.

**데이터 축**

- `measurement` / `tech_option` 정규화 테이블과 인덱스 2개 —
  비교·집계 화면이 없는데 정규화부터 하면 첫 주가 사라진다. 측정값과 후보는
  `body`·`outcome` 안의 텍스트로 받는다.
- `measurement.py`(`MeasurementInput` · `OptionInput` · `delta_of`) —
  위 테이블을 읽는 코드가 없으면 개선률 계산도 쓸 데가 없다.
- `mitigation` 컬럼 — 컬럼 자체를 두지 않는다. 단점 보완은
  `rationale`·`limitation` 안의 문장으로 받는다.

**규칙 축**

- `record_rules.py` 의 `missing_fields(kind, values)` — kind 별 필수 필드 규칙.
  이번의 `topics.missing_fields` 는 kind 를 보지 않는 단순판이다.
- kind 별 MCP 툴 4개 분화(`record_experiment` 등) —
  툴 표면적이 넓을수록 '기록 안 하기'가 이긴다. 명확함은 툴 수가 아니라
  응답에 실어 보내는 힌트로 얻는다.
- 필수 필드 미비 시 MCP 단계 거절(2026-08-12 스펙 §7) —
  거절당한 에이전트가 실제로 하는 일은 '다시 채우기'가 아니라 '그냥 넘어가기'다.

**주차 축**

- `daemon/derive.py` 의 `week_of` · `week_bounds` — 주차는 글을 쓰는 데 필요 없다.
  경계 테스트(KST 자정 4줄)는 되살릴 때 그대로 쓸 수 있으니 이전 판 히스토리에서 꺼낸다.
- `Settings.roadmap_start_date` 와 `load_or_create_daemon_config` 반환 형태 변경 —
  위 계산이 없으면 설정만 남는다. 호출부를 건드리는 변경이라 값 없이 하지 않는다.
- 학습 진도 추적 · 다음 주제 추천 · 분야별 커버리지 대시보드 —
  기록이 몇 주 쌓여 실제 데이터가 생긴 뒤에 설계해야 형태가 나온다.

**화면 축**

- `/records` 목록·상세와 필터(`project`·`kind`·`tag`·`week`·`missing`) —
  이번 화면의 축은 필터가 아니라 주제와 날짜다.
- `list_records` / `get_record` 조회 툴 — `get_topic_records` 하나가 다듬기에 필요한 전부다.
- `?missing=interview` 복습 큐와 `⚠ 면접 문장 없음` 배지 —
  같은 정보를 `/t/{slug}` 의 '부족한 필드' 목록이 초안 만들기 직전에 보여준다.
- 기록의 soft delete 웹 폼과 `?deleted=1` — 컬럼(`deleted_at`)은 두되 화면은 만들지 않는다.
- `back` 쿼리스트링 복귀 규칙 — 돌아갈 곳이 필터 조합이 아니라 `/t` 하나라 필요 없다.
- `topic` 별칭 병합 UI — slug 정규화로 대부분 잡히고 남는 소수는 SQL 한 줄이 화면보다 싸다.

**발행 축**

- `GitPrivateRepoTarget` — 2순위. 첫 한 바퀴가 돈 직후 착수하되
  **MVP 완료 판정에는 포함하지 않는다.** 기존 ssh/gh 자격증명을 그대로 쓰므로
  새 토큰 저장소도 OAuth 도 필요 없고 코드는 파일 쓰기 + subprocess 수준이다.
- **직접 만드는 티스토리 MCP** — 사용자가 만들기로 정했다(2026-08-18).
  파이썬으로 만들면 추가 런타임이 0 이다(`mcp` 는 이미 의존성, 이 머신에 Node 는 없다).
  단 이번 MVP 범위 밖이다. 첫 스파이크는 '글 작성'이 아니라
  '카카오 세션이 며칠 재사용되는가' 측정이고, 세션이 3일을 못 버티면
  그날 바로 멈추고 붙여넣기로 되돌아온다.
  약관 원문 확인이 선행 조건인데 정책 URL 이 404 라 **확인 못 했다.**

  `PublishTarget` 만 있으면 나중에 파일 하나다. MVP 의 가치는 어댑터 개수가 아니라 종단 경로 1개.
